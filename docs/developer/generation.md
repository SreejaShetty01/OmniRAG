# Grounded generation and verification

Use `AnswerPipeline.answer(query, retrieval_result)` with the Phase 3 `RetrievalResult`. The pipeline short-circuits insufficient evidence, then calls a provider-neutral `ChatProvider` through `AnswerGenerator`. Provider-specific HTTP details are isolated in `OpenAICompatibleChatProvider`; deployments may inject another implementation. Configure generation and verification slots separately through `OMNIRAG_GENERATION_*` and `OMNIRAG_VERIFICATION_*`. No model ID, endpoint, or credential is selected by default.

Generation receives a trusted system instruction separately from JSON-serialized evidence inside explicit untrusted delimiters. Retrieved passages are treated as data, and suspicious instruction patterns produce a warning. This is a defense-in-depth measure, not a guarantee against prompt injection. Structured output names claim text and evidence IDs; IDs are resolved only against Phase 3 evidence. Invalid IDs are marked unsupported and removed from inline answer markers. Citations are built deterministically from the resolved evidence and include document, chunk, source, title, page, section and excerpt fields where available.

Claim verification includes citation resolution, conservative numeric and identifier presence checks, and an optional provider-neutral entailment interface. Without a configured semantic verifier, claims remain uncertain; provider errors also remain uncertain and produce warnings. Numeric presence alone is not treated as semantic support. Evidence contradiction signals currently detect related passages containing differing numeric values and preserve source/version metadata; they are heuristic flags, not a complete contradiction model.

At most one correction attempt is made for unsupported or contradicted claims. If those claims remain after correction, the pipeline abstains. Insufficient retrieval evidence causes abstention without a provider call. Partial and conflicting evidence can be answered with explicit limitations. Retrieval sufficiency is preserved separately from claim verification and overall reliability.

Before generation, the pipeline also checks internally mixed-case names and context-indicated title-case names (for example, a name after “of” or “called”) against selected evidence. This avoids treating ordinary title-cased document terms as entities. If a detected query entity is absent, it abstains without calling the generation provider. An explicitly parenthesized query alias such as “International Business Machines (IBM)” is accepted when the alias appears in selected evidence. This remains a lexical guard, not semantic entailment or general entity resolution: unmarked aliases, paraphrases, and indirect references that omit the queried name can still be rejected. Claims without a detected proper name continue through the existing citation and claim-verification behavior. Tests cover missing and supported JPMorgan cases, an explicit acronym alias, ordinary title-cased document words, and a normal Lite query without named entities.

The response extends `OmniRAGResponse` with defaulted fields for response ID, original query, claim states, reliability, abstention reason, contradiction details, model metadata, token use, timings and warnings. Existing fields and defaults remain. Usage is reported when supplied by a provider. Costs remain unset unless a provider adapter supplies an actual cost value.

`evaluation.generation_benchmark` provides metrics for separately curated labeled cases. The repository contains no human-labeled answer/evidence gold set, so no generation quality or verification effectiveness scores are claimed. The basic tests use mocked chat and entailment providers; live provider behavior is unverified. Existing Phase 3 Windows async retrieval and real reranker limitations are unchanged.
