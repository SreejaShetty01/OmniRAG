# Retrieval engine

`retrieval.HybridRetriever` is the single shared entry point. Call `retrieve(query, scope=RetrievalScope(...), policy=...)`; callers must supply at least one authenticated principal. The engine analyzes explicit query directives, constructs active-generation and ACL filters, embeds once, runs dense and sparse searches, fuses with deterministic RRF, applies configurable structural overlap, deduplicates, optionally reranks, expands one hop, selects evidence within count/token limits, and emits an uncalibrated sufficiency assessment with provenance and timings.

The engine uses the existing Qdrant `dense` and `sparse` names and Phase 2 payload. The hashed sparse tokenizer is intentionally unchanged; it tokenizes `\\w+` runs and hashes terms, so punctuation is separators, identifier substring matching is not supported, and hash collisions remain possible. No index migration is introduced in this phase.

ACL filters are applied inside dense, sparse, and every expansion query. Points must be active, allow lists must be empty or match a caller principal, and a deny match always excludes the point. Tenant and workspace scope are enforced when supplied. Explicit document, source, type, language, version, collection and section filters are supported. Callers should supply a corpus generation to enable result caching; without one the cache is bypassed to avoid stale evidence.

Structural scoring is disabled by default (`structure_weight=0`) until evaluated against representative gold data. Parent expansion is enabled by default; children, neighbours and cross references are policy-controlled. Expansion is one hop and obeys its own count/token budget. Reranking is optional and provider-neutral through the HTTP adapter contract; a configured adapter failure falls back to fused ranking with a warning. Sufficiency states are heuristic signals, not calibrated probabilities; RRF scores are never interpreted as confidence.

`evaluation.retrieval_benchmark` supplies labeled-case metrics and an injected variant runner for dense-only, sparse-only, hybrid, structural, expansion and reranking comparisons. No representative retrieval gold set is included and no quality score is claimed. The benchmark should be run against a separately maintained, access-controlled dataset. Qdrant in-memory integration verifies dense/sparse filtering and structural expansion; production Qdrant server and external reranker behavior require deployment-level verification.
